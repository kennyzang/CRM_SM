# 术语核对表 — 手册用词 vs 线上实际文案

> 状态：进行中
> 方式：联系人/线索两个模块由 AI 用 Playwright 直接登录 CRM（soo 账号，中文界面）实地探查列表页/详情页/按钮，记录真实文案；其余模块可由用户手动操作/截图后告诉我，我来记录整理，不自行猜测线上文案
>
> **重要踩坑记录**：手册里给的模块直达链接（如 `wiki/user-manuals/zh/contact-manual-zh.md` 里的联系人链接、lead-manual-zh.md 里的线索链接）直接用 URL 跳转会白屏卡死，必须先进入 CRM 首页再通过左侧/顶部导航菜单点击进入，才能正常加载对应列表页。这个问题本身也要记录，因为如果手册里教用户"点这个直达链接"，而实际会白屏，那手册这条也要改。

## 记录格式说明

请按模块告诉我：
- 页面位置（如：线索详情页 / 客户列表页）
- 你看到的真实按钮/字段/状态文案（可以直接截图，我会读图确认文字）
- 对应手册里的说法是什么（如果你知道；不知道我可以去 `wiki/user-manuals/zh` 查对应章节）

我会逐条填进下表，只记录你确认过的真实内容，不填不确定的猜测。

## P&L 分类标签——源码定案（不再是猜测）

P&L 是一个自定义前端组件，源码在 `/Users/xiex/Documents/GIT/OVERSEABU/portal-custom-element/packages/securemetric-crm-pl`，不属于本仓库但用户直接指出了路径。直接读 `src/constants.ts` 里的 `TAB_CONFIGS` 常量，是唯一权威的真相来源（比手册、比 schema、比截图都准，因为这就是渲染 UI 用的那份配置本身）。

**结论：实际标签是 9 个，不是手册说的 7 个：**

| 序号 | 标签 key | 标签文案（英文，写死无中文） | 下设2个子表 |
|------|---------|---------------------------|------------|
| 1 | overview | Overview | — |
| 2 | software | Software | SM Products / 3rd Party Software |
| 3 | softwareRenew | **Software Renew**（手册没有这条） | SM Products / 3rd Party Software |
| 4 | hardware | Hardware | SM Products / 3rd Party Hardware |
| 5 | hardwareRenew | Hardware Renew | SM Products / 3rd Party Hardware |
| 6 | service | Services | SM Services / 3rd Party Services |
| 7 | serviceRenew | **Services Renew**（手册没有这条） | SM Services / 3rd Party Services |
| 8 | reimbursement | Reimbursement | SM Team / 3rd Party Team |
| 9 | others | Others | Other Costs |

**之前的疑问已解开**：schema 里看到的"软件自研/软件第三方/硬件自研/硬件第三方/服务自研/服务第三方"6个字段，其实不是6个平行标签，而是 Software/Hardware/Services 这3个标签**各自内部**的"SM Products（自研）vs 3rd Party（第三方）"两个子表——schema 之所以只看到6个（没看到 Renew 的另外6个 + Reimbursement/Others 的3个，一共15个数据子表），是因为 `custom_pl_profit` 是自定义组件，通用 schema 生成器抓不到它内部动态渲染的完整字段，只能看到主表面上暴露的那几个。

**额外发现（源码里查到，手册和实测都没提到）**：
- `src/locale/zh-cn.json` 是**空文件 `{}`**，`langs.ts` 里也没有覆盖这些标签——即这9个标签在系统里**永远显示英文**，不会因为切换到中文界面而变化，这个可以直接写进用例断言，不用再截图验证。
- Software Renew / Hardware Renew / Services Renew 三个 Renew 标签有"一键复制"逻辑（`copySourceTab` 字段指向对应的非 Renew 标签），即 Renew 标签的数据来源是从对应主标签"复制"过来的，这个业务逻辑手册完全没提，值得写一条用例覆盖"续期复制"这个功能点。
- `SECUREMETRIC_PRINCIPAL_ID` 硬编码了一个 Principal（供应商主体）的 fdId，用来自动判断某条产品记录该分到"SM Products"还是"3rd Party"子表——如果这个 Principal 记录被误删或改名，可能导致产品分类逻辑出错，这是一个潜在的技术风险点，可以作为边界用例的输入（虽然不是常规业务测试范围，但值得记录在案）。

## 已确认的通用结论（可直接用于后续用例撰写）

- 本地化程度**逐模块、逐字段参差不齐**：同一系统里，线索模块的"服务团队/销售记录"显示英文，联系人、客户、商机模块的同类概念却显示中文；写用例断言文案时必须以**该模块实测结果**为准，不能跨模块套用。目前看下来，**商机模块本地化程度最好**（详情页头部、阶段名手册都标注了对应英文且完全吻合），**线索模块本地化程度最差**（详情页大量字段是英文）。
- 手册记录的按钮显示条件/名称（负责人操作、公海/线索池管理员操作那一批）与实测**高度吻合**，可信度高，可以直接引用手册作为用例的操作步骤依据，这个结论在线索、联系人、客户三个模块上都得到验证；但手册记录的字段名、列表列、标签页名称与实测**出入较多**，这部分必须逐条实测，不能直接抄手册。
- **商机手册的"中文（English）"标注格式是最佳实践范例**：商机手册在视图标签、阶段名称上都同时写了中文和英文，实测结果与英文部分完全吻合。建议后续修订线索/联系人/客户手册时，统一改成这个"中文（English）"格式，而不是只写中文。
- 手册里的模块直达链接会导致页面白屏，需要通过导航菜单点击进入；这个问题建议反馈给手册维护者一并修正。
- 系统存在简繁混用现象（客户模块二级菜单"客戶"用繁体，一级菜单"客户管理"用简体），这不是手册的错，但写术语表时要如实记录，不要自行"纠正"成统一简体。
