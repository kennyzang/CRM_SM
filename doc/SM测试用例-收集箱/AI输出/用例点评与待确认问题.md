## 二、用户能否"一看就懂"？

### 详细中文用例（TC-001 ~ TC-010）→ 基本可理解

步骤较完整，有具体数字校验点，配合业务背景可执行。但仍存在部分描述可以更精确（见下文三）。

### 基础功能用例（admin_en/）→ ❌ 看不懂

以 `admin_en/lead.yaml` 为例：

```yaml
steps: '1.List
    2.New
    3.Name/Pool/Type/Source/Level/Details/Pipeline/DealCat
    4.Products
    5.Save'
```

问题：

1. **"1.List"** —— 去哪个页面？菜单路径是什么？
2. **"3.Name/Pool/Type/..."** —— 只列字段名，没说要填什么值，没区分"点击""输入""选择"
3. **"1.Saved"** —— 保存后看到什么？提示消息？页面跳转？状态变化？

## 三、具体问题清单

### 问题 1：基础用例缺少操作对象定位

- 现状：`1.List`、`1.Detail`、`2.Click views`
- 影响：测试人员不知道从哪里开始操作
- 建议统一格式：`1.左侧导航 → 销售管理 → 线索` → `2.点击「新建」按钮（页面右上角）`

### 问题 2：基础用例缺少测试数据具体值

- 现状：`Name/Pool/Type/Source/Level`（只列字段名，没写填什么）
- 影响：不同人执行结果可能不同，重复执行可能因数据冲突失败
- 建议：
  ```
  线索名称: "测试线索-Auto-{时间戳}"
  来源: "搜索引擎"
  等级: "A级"
  ```

### 问题 3：预期结果过于笼统

- 现状：`1.Saved`、`1.Tabs correct`、`1.Filtered`
- 影响：无法判断测试是否真正通过，缺少可量化的判定标准
- 建议：
  ```
  1. 页面顶部弹出绿色成功提示「保存成功」
  2. 列表页出现新记录，名称与输入一致
  3. 状态字段显示为「待跟进」
  ```

### 问题 4：YAML 格式多余空行

现状（每行 step/expected 之间有额外空行）：

```yaml
steps: '1.List

    2.New
    ...
```

渲染后产生多余空白，影响可读性。

### 问题 5：用例颗粒度不一致

| 粒度过粗 | 粒度适中 |
|---------|---------|
| TC-LEAD-002: "Leave all required fields empty" — 一个用例测所有必填 | TC-CONTACT-003/004: "仅填手机"和"仅填邮箱"分两个用例 |

### 问题 6：前置条件不够具体

- `Has related data`（有什么关联数据？几条？）
- `Multiple records`（几条记录？）
- `Owner of A`（A 是谁？数据 ID 是多少？）

### 问题 7：admin_en 中中英混存

`admin_en/lead.yaml` 文件前 10 条（TC-LEAD-001 ~ TC-LEAD-010）是纯英文，后面 5 条（TC-001 ~ TC-005）是中文名 + 中文描述。

### 问题 8：缺少异常/边界路径

- 格式校验：邮箱格式、手机号格式、注册码格式
- 边界值：最大字符数、全角/半角符号
- 重复操作：重复提交、并发操作
- 中断恢复：保存过程中断、页面刷新

### 问题 9：缺少跨模块依赖标注

- `TC-INVOICE-001` 前提「SO exists」—— 没有关联前置用例
- 追索时测试人员需要自己先准备上游数据

### 问题 10：admin_en 与 zh 信息量不对等

- admin_en 版极简，zh 版详细程度明显更高
- 两者不是简单的翻译关系，信息量差距大
